下面我按你的 mermaid 流程，把 **LangGraph 的“主图 + 3 个子图（解析子图 / 抽取子图 / 入库子图）”**拆出来，并把每个节点的 **State 输入输出、边、条件路由、循环方式**都对应到 A~I。

---

## 0. 总体设计：一个主图 + 三个子图

### 主图（OrchestratorGraph）

负责：校验、落盘、建 Job、串起 3 个子图、最终通知。

* **子图 1：ParsePdfSubgraph（Agent-1）**
  逐页把 PDF → Markdown + 元数据，落 OSS 中间产物，写 MySQL 进度。
* **子图 2：ExtractInfoSubgraph（Agent-2）**
  逐页读 Markdown，做跨页连续性判断 + Memory 状态管理，产出结构化候选结果，最后汇总 JSON。
* **子图 3：IngestSubgraph**
  MySQL 主表/版本/审计、ES、Milvus、OSS 归档、回调通知。

---

## 1. State 设计（强烈建议：主 State + 子图局部 State）

### 1.1 主图 GlobalState（贯穿全流程）

建议至少包含：

* **身份与资源**

  * `tenant_id: str`
  * `doc_id: str`
  * `job_id: str`
  * `uploader_id: str`（可选）
* **OSS key / bucket**

  * `raw_pdf_oss_key: str`（`raw_bucket/tenant_id/doc_id.pdf`）
  * `md_prefix: str`（`md_bucket/tenant/doc/`）
  * `final_json_oss_key: str`
* **分页与进度**

  * `page_count: int`
  * `parse_progress: {page_done:int, quality:float, parser_used:str, ...}`
  * `extract_progress: {page_done:int, ...}`
* **结果与证据**

  * `page_md_keys: list[str]`（每页 md 的 OSS key 列表）
  * `extracted_company: dict`
  * `extracted_products: list[dict]`
  * `evidence: list[dict]`（证据引用：页码、md片段、chunk_id 等）
  * `final_structured_json: dict`
* **错误与审计**

  * `errors: list[dict]`
  * `trace: list[str]`（可选：节点执行轨迹）

> 关键点：**page_md_keys** 是 Parse 子图输出给 Extract 子图的“契约”。

## 2. 主图 OrchestratorGraph：节点与边（对应 A→I）

### 节点清单（对应你的 A/B/C/D…）

1. **A_upload_pdf**（入口：拿到上传请求/文件句柄/上传事件）
2. **B_validate_gateway**：校验租户/权限/大小/格式
3. **C_save_raw_pdf_to_oss**：存 raw_bucket
4. **D_create_job_mysql**：写 MySQL 任务表（job_id, doc_id, tenant_id, status=RUNNING）
5. **E_parse_subgraph**：调用 ParsePdfSubgraph（Agent-1）
6. **F_extract_subgraph**：调用 ExtractInfoSubgraph（Agent-2）
7. **G_build_final_json**：汇总 company+products+evidence，生成最终 JSON
8. **H_ingest_subgraph**：调用 IngestSubgraph
9. **I_notify_callback**：任务完成回调/通知（成功/失败）

### 主图边

* `START -> A -> B -> C -> D -> E_subgraph -> F_subgraph -> G -> H_subgraph -> I -> END`
* 任意节点失败：可统一路由到 **FailHandler**（可选节点）更新 MySQL 状态并通知失败。

## 3. 子图 1：ParsePdfSubgraph（Agent-1，逐页解析循环）

### 子图目标

* 输入：`raw_pdf_oss_key / tenant_id / doc_id / job_id`
* 输出：`page_count`、`page_md_keys`、`parse_progress(最终)`，以及每页元数据（可选）

### 节点拆分（对应 E1~E5）

* **E1_download_pdf_signed_url**

  * 产出：`pdf_local_path` 或 `pdf_bytes`，以及 `signed_url`
* **E2_parse_page_router**（循环控制节点：决定解析下一页 or 结束）

  * 读取：`current_page`、`page_count`
  * 输出：路由到 `E2_parse_single_page` 或 `END_SUBGRAPH`
* **E2_parse_single_page (ReAct)**

  * 逻辑：文本层优先；必要时 OCR（可根据 page quality 判断）
  * 输出：`page_md_content`、`page_meta`（标题/表格/图像位置/置信度/是否OCR）
* **E3_build_page_markdown**

  * 输出：标准化 Markdown（比如统一 heading、表格、图片占位符），以及结构元数据
* **E4_write_page_md_to_oss**

  * 输出：`page_md_key`（`md_bucket/tenant/doc/page_n.md`）
  * 同时 append 到 `page_md_keys`
* **E5_update_mysql_parse_progress**

  * 写：`page_done, quality, parser_used`
  * 输出：更新 `parse_progress`

### 子图循环方式（LangGraph 推荐）

* 用 `current_page` 放在 State 里：从 1 开始
* `E5` 执行完把 `current_page += 1`
* 回边：`E5 -> E2_parse_page_router`

**ParsePdfSubgraph 的结构：**

* `START -> E1 -> E2_router -> E2_single -> E3 -> E4 -> E5 -> (loop back to E2_router) -> END`

> 解析子图的“可扩展点”：
>
> * page parsing 可拆成：`extract_text_layer`、`detect_need_ocr`、`run_ocr`、`merge_layout`
> * 但你这张图里保持 E2 一体化也可以。

## 4. 子图 2：ExtractInfoSubgraph（Agent-2，逐页抽取 + Memory + 连续性判断）

### 子图目标

* 输入：`page_md_keys`（或 md_prefix + page_count）
* 输出：`extracted_company`、`extracted_products`、`evidence`，以及抽取进度

### Memory / 状态管理（对应 F2）

建议在子图 State 里维护一个 **ExtractMemory**：

* `company_profile: dict`
* `products: dict[str, dict]`（用 product_id 或规范化名称做 key）
* `current_context: dict`（当前抽取对象：产品/章节/字段填充进度）
* `last_page_summary: str`（帮助跨页连续性判断）
* `normalization_rules: dict`（单位统一/别名映射）

### 节点拆分（对应 F1~F8 + 循环）

* **F1_load_page_md**

  * 输入：`current_page` 或 iterator
  * 输出：`page_md_content`
* **F2_update_memory_context**

  * 生成页级摘要/候选对象线索（章节标题、产品名候选、表格字段候选）
  * 更新 `last_page_summary`、`current_context` 的“提示材料”
* **F3_decide_continuity (condition)**

  * 输出：`route = "continue" | "new_object"`
  * 判断依据：产品名/章节标题/表格主键/上一页对象未闭合标志等
* **F4_continue_object**

  * 继续补全同一产品/同一章节字段（把当前页信息融合进 `current_context`）
* **F5_finalize_prev_object**

  * 将上一个对象收束写入候选结构化结果（落到 `products` 或 `company_profile`）
* **F6_init_new_object**

  * 初始化新对象：新产品 or 公司模块（更新 `current_context`）
* **F7_extract_fields_validate (ReAct + Memory)**

  * 字段抽取与校验：规格/参数/卖点/性能等重点
  * 输出：抽取字段、字段置信度、证据引用（页码/行/片段）
* **F8_conflict_dedup_normalize**

  * 冲突处理：同名产品合并、重复参数去重、单位统一（mm/cm、W/kW…）
  * 输出：更新后的 `company_profile/products` + `evidence`
  * 同时更新 MySQL 抽取进度（可在此节点内或单独一个节点）

### 子图循环方式

* 和 Parse 子图一样维护 `current_page`
* `F8` 后 `current_page += 1`，回到 `F1`
* 当 `current_page > page_count`：

  * 先走一个 **FinalizeTailObject**（把未闭合的 current_context 收束）
  * 再 `END_SUBGRAPH`

**ExtractInfoSubgraph 的结构：**

* `START -> F1 -> F2 -> F3 -> (continue: F4 -> F7 -> F8) OR (new: F5 -> F6 -> F7 -> F8) -> loop to F1 -> END`

> 实战建议：
>
> * F3 连续性判断不要只靠 LLM：可以先规则/embedding 相似度，LLM 做裁决。
> * evidence 最好结构化：`{page, md_key, quote, field, object_id}`，方便 ES/Milvus/审计。

## 5. 节点 G：生成结构化 JSON（对应 G）

这个建议放在主图里做（因为它是“跨子图结果汇总”）。

**G_build_final_json**：

* 输入：`extracted_company`、`extracted_products`、`evidence`
* 输出：`final_structured_json`
  建议 schema：

```json
{
  "tenant_id": "...",
  "doc_id": "...",
  "job_id": "...",
  "company": {...},
  "products": [{...}, {...}],
  "evidence": [{...}],
  "meta": {
    "page_count": 12,
    "parser": {...},
    "timestamps": {...},
    "version": "v1"
  }
}
```

## 6. 子图 3：IngestSubgraph（对应 H1~H4）

### 子图目标

把最终 JSON + 中间产物在各存储系统落地，并保证幂等与审计。

### 节点拆分（对应 H1~H4）

* **H1_write_mysql_main_tables**

  * 写：结构化主表、版本表、审计表（job_id、hash、操作者、时间）
* **H2_index_elasticsearch**

  * 写：全文检索（原文 chunk + 提取字段 + evidence 链接）
* **H3_upsert_milvus_embeddings**

  * 写：产品/段落 embedding
  * 建议：embedding 在这里算或提前算；但要确保可重放（同 doc_id+version 幂等）
* **H4_archive_to_oss**

  * 写：最终 JSON + 解析产物归档（包括 md、元数据、日志摘要）

### 子图并行（推荐）

H1/H2/H3/H4 其实可以并行，只要你能接受最终一致性：

* LangGraph 里可以用“并行分支”写法：从一个节点 fan-out 到多个节点，再 join 到 `END`。
* join 节点负责汇总各分支的执行状态，失败则标记部分失败并写审计。

## 7. I 节点：回调/通知（对应 I）

**I_notify_callback**

* 输入：`job_id`、`status`、`final_json_oss_key`、关键统计（页数/耗时/质量）
* 输出：无（或写 trace）
* 同时更新 MySQL：`status=SUCCEEDED/FAILED`、`finished_at`

## 8. 关键工程点（你后面落地会省很多坑）

### 8.1 幂等键（强烈建议统一）

* `tenant_id + doc_id + version` 做“结构化版本幂等键”
* `job_id` 做本次任务流水
* ES/Milvus/MySQL 全部用同一个幂等键，便于重跑和回滚。

### 8.2 子图边界的“契约字段”

* Parse → Extract：`page_md_keys + page_count + parse_quality`
* Extract → Ingest：`final_structured_json + extracted_* + evidence + version`

### 8.3 失败策略

* Parse 子图：单页失败可重试（OCR fallback），超过阈值标记质量下降但继续
* Extract 子图：单页失败可降级（只抽取显式表格字段）
* Ingest 子图：允许部分失败，写审计 + 可重试队列

### 8.4 建议的节点粒度

* 你图里的节点粒度已经很接近可实现粒度
* 真正落地时：把“外部 IO 节点”和“LLM 节点”分开（更易重试与观测）
