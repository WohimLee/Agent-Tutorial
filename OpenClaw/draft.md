

## 十二、真正执行：推理、工具调用与流式响应

当上下文准备完毕后，Agent 才真正开始运行。

在示例场景中，模型可能会判断：

* 当前任务不是普通问答
* 它是一个执行型任务
* 其中包含邮件整理、待办提炼、简报生成三类需求
* 需要调用相应技能与工具
* 如果任务过于复杂，可能还要拆给子 Agent

这一阶段的核心有三件事：

### 1. 流式响应

OpenClaw 使用 SSE 或 WebSocket 做流式输出。

当 LLM 开始生成内容时，系统会把内容块实时推送给客户端，让用户立即看到输出开始，而不是等待全部完成后一次性返回。

### 2. 工具调用

当 LLM 判断需要调用工具时，系统会暂停文本流并执行对应工具，例如：

* 读取文件
* 调 API
* 搜索记忆
* 访问邮件
* 执行脚本

工具执行完成后，再将结果反馈给 LLM，继续推理。

这实际上形成了一次完整的：

> 推理 → 执行 → 再推理

循环。

### 3. 错误处理与模型回退

生产环境中错误是常态，因此 OpenClaw 做了多级回退：

* 限流：指数退避或切换备用模型
* 认证错误：轮换多个 API Key
* 超时错误：降低 thinking 级别或改用更快模型
* 上下文溢出：触发压缩或切换更大上下文模型

这体现了其强烈的工程取向：不假设模型永远稳定，而是假设运行过程随时可能失败。

## 十三、任务完成后的收尾动作

当 Agent 完成任务后，系统还不能立刻结束，还需要做三类收尾。

### 1. 响应投递

回复分发器会根据消息上下文中的来源通道与目标地址，调用对应通道的出站适配器发送消息。

如果配置了跨通道回复，也可以覆盖原始目标，例如：

* 在钉钉发起任务
* 最终把结果发回 WhatsApp

这体现出 OpenClaw 的智能网关特征，而不只是聊天窗口中的模型。

### 2. 会话持久化

系统会把这次交互完整记录下来：

* 更新 `sessions.json` 中的元数据
* 将用户消息、AI 回复、工具调用等内容追加到 JSONL 转录文件

这样下一次会话继续时，系统才能知道之前发生了什么。

### 3. 资源释放与清理

执行结束后，还要做：

* 释放会话车道锁
* 释放全局并发配额
* 标记幂等键为已处理
* 定期清理过期会话
* 归档旧转录
* 轮换大文件

这些动作属于长期运行系统的善后逻辑。

## 十四、记忆索引：让 Markdown 变成可检索知识库

既然记忆以 Markdown 文件形式存在，系统还需要解决一个问题：

> Agent 如何高效检索这些记忆？

OpenClaw 的做法是为记忆系统单独建立索引，索引数据库通常位于：

```text
~/.openclaw/memory/index.db
```

数据库中通常包含以下表：

* `files`
* `chunks`
* `chunks_vec`
* `chunks_fts`
* `embedding_cache`

这意味着系统同时支持：

* 文件元数据管理
* 文本分块
* 向量检索
* 全文搜索
* 向量缓存

### 索引同步机制

为保证文件和索引同步，系统会采用：

* 文件监视器自动触发
* 定期同步
* 增量同步

必要时还会进行全量重建：

1. 创建临时数据库
2. 遍历记忆文件
3. 文本分块
4. 生成 embedding
5. 建立全文索引
6. 原子替换旧索引

因此，OpenClaw 的记忆不是把 Markdown 当作普通备忘录，而是将其构造成一层可检索、可维护的知识基座。

## 十五、多 Agent：从单 Agent 闭环走向层级协作

到目前为止，已经形成了一条完整的单 Agent 执行链路：

1. 消息进门
2. 协议适配
3. 去重拦截
4. 路由分发
5. 会话排队
6. 上下文组装
7. 技能注入
8. 流式执行
9. 响应投递
10. 状态持久化

如果任务简单，到这里就闭环了。

但现实中的复杂任务，往往并不适合由一个 Agent 独立完成。

例如：

> 帮我整理今天的重要邮件，提炼待办，并生成一份给老板的简报。

看似一句话，实际上可能至少包含三块工作：

* 筛选和归类邮件
* 提炼关键待办
* 组织成适合老板阅读的简报格式

如果全部交给一个 Agent，虽然也能完成，但容易出现：

* 上下文太重
* 推理链过长
* 工具调用过杂
* 专业能力混在一起
* 中间状态难以管理

因此 OpenClaw 在单 Agent 之上又构建了 **多 Agent 协作系统**。

### 多 Agent 的核心能力

它主要实现了：

* Agent 隔离
* 动态任务分发
* 层级协作
* 生命周期管理
* 安全边界控制

也就是说，主 Agent 可以根据任务需要，临时创建一个或多个子 Agent，把部分子任务交出去，自己负责总控和汇总。

### 一个典型流程

在示例任务中，主 Agent 可能这样拆分：

1. 创建 `research-agent` 去筛重要邮件
2. 创建 `analysis-agent` 去提炼待办与风险点
3. 由主 Agent 汇总结果并组织成面向老板的简报

这时，多 Agent 不再是抽象概念，而是一种具体的任务拆解策略。

## 十六、SubAgent 的创建与返回机制

当主 Agent 决定创建子 Agent 时，通常会调用 `sessions_spawn` 工具。

系统会先做一轮严格校验：

* 嵌套深度检查，防止无限递归
* 并发限制检查，防止资源耗尽
* 允许列表检查
* 沙箱状态检查

通过后，系统会执行以下动作：

### 1. 生成唯一子会话键

例如：

```text
agent:{agentId}:subagent:{uuid}
```

### 2. 应用模型配置与 thinking 级别

并处理附件与上下文传递。

### 3. 为子 Agent 生成专门的系统提示词

```text
# Subagent Context
You are a subagent spawned by main agent for a specific task.
## Your Role
- You were created to handle: ${taskDescription}
- Complete this task. That's your entire purpose.
- You are NOT main agent. Don't try to be.
## Rules
1. Stay focused
2. Complete task
3. Don't initiate
4. Be ephemeral
```

这个提示词强调的不是人格，而是边界：

* 你不是主 Agent
* 你只负责一个具体子任务
* 你是临时性的

### 结果返回

子 Agent 完成任务后，系统会：

* 触发生命周期事件
* 读取输出结果
* 经过通知队列
* 判断目标是谁
* 决定注入主 Agent 会话，还是直接发给用户

如果请求者是主 Agent，那么结果通常会以内部事件的方式重新注入主 Agent 会话，供主 Agent 在下一轮推理中使用。

于是整条协作链路就变成：

1. 主 Agent 接收用户任务
2. 主 Agent 拆分子任务
3. 子 Agent 分别执行
4. 子 Agent 回传结果
5. 主 Agent 汇总结果
6. 主 Agent 最终回复用户

这本质上就是一个层级化协作网络。

## 十七、配置继承机制

OpenClaw 在 Agent 配置上采用三级继承：

1. Agent 级配置优先级最高
2. 全局默认配置次之
3. 代码默认值兜底

例如某个 `coding-agent` 可以独立配置：

* 模型
* 工作区
* 可用工具
* 子 Agent 策略
* 沙箱模式

未单独定义的部分再回落到全局默认值。

这种设计让多 Agent 系统既灵活，又不至于配置爆炸。

## 十八、OpenClaw 的核心价值

回到最初那句任务：

> 帮我整理今天的重要邮件，提炼待办，并生成一份给老板的简报。

在 OpenClaw 中，它真正经历的大致流程是：

1. 钉钉原始消息进入系统
2. 通道插件把它适配成统一的 `MsgContext`
3. 网关做最终化处理
4. 系统检查去重、拦截控制命令、快速响应 `started`
5. 路由系统根据绑定规则找到目标 Agent
6. 生成 `sessionKey`
7. 进入会话车道排队，确保同一会话不乱序
8. 组装完整上下文：系统提示词、Bootstrap 文件、Skills、历史记录、当前消息
9. 模型在技能描述和规则约束下开始推理
10. 过程中可能调用工具，也可能创建子 Agent
11. 子 Agent 完成后将结果回流给主 Agent
12. 主 Agent 生成最终答复
13. 回复分发器把结果投递回目标通道
14. 会话与转录被持久化
15. 记忆被更新，索引同步
16. 资源释放，执行闭环结束

由此可以看出，OpenClaw 的真正价值不在于“能不能回答一句话”，而在于：

> 它把一条消息从进入系统到完成执行，做成了一条可治理、可扩展、可追踪、可恢复的 Agent Runtime 链路。

---

## 十九、结语

通过完整追踪一条消息的旅程，可以更清楚地看到 OpenClaw 的几个核心设计原则：

### 1. 分层

各层职责清晰，从通道适配到执行治理，再到基础设施，边界明确。

### 2. 运行时导向

去重、会话车道、上下文压缩、错误回退、资源清理等机制说明，它不是一个“给 prompt 套一层 UI”的玩具，而是在认真处理长期运行中的工程问题。

### 3. 可扩展

通道插件、技能系统、子 Agent 机制、记忆索引，让它更像一个开放的 Agent 网关，而非封闭应用。

### 4. 具备分布式协作雏形

多 Agent 的引入，意味着 OpenClaw 已不满足于“一个模型处理一切”，而是在朝任务拆解、层级协作、并行执行的方向演进。

所以如果要概括 OpenClaw，可以这样定义：

> 它不是一个更会聊天的机器人，也不只是一个会调工具的 Agent 外壳。它更像是一个把消息入口、会话治理、上下文管理、技能调用、持久化存储和多 Agent 协作整合在一起的 **Agent Runtime + Gateway**。
