## function call & MCP
### 一、什么是 Function Call（函数调用）
##### 1️⃣ 基本定义

- Function Call 是指：大模型在生成回复时，不是输出自然语言，而是输出一个结构化的“函数调用请求”，由宿主程序去真正执行这个函数。
- 简单说就是：模型负责“决定要干什么”，程序负责“真的去干”

##### 2️⃣ 为什么要有 Function Call

传统 LLM 的问题是：
- 只能“说”，不能“做”
- 输出不可控（自然语言，不适合直接执行）
- 很难和真实系统（数据库 / API / 业务逻辑）对接

Function Call 解决的是：

| 问题  | 解决方式          |
| --- | ------------- |
| 调接口 | 输出 JSON 而不是文本 |
| 可控性 | 严格匹配函数 schema |
| 自动化 | 模型决定调用哪个函数    |
| 安全性 | 模型不能直接执行代码    |


##### 3️⃣ 一个典型例子


```py
# 你定义函数
{
  "name": "get_weather",
  "description": "查询城市天气",
  "parameters": {
    "type": "object",
    "properties": {
      "city": { "type": "string" }
    },
    "required": ["city"]
  }
}

# 用户说：北京今天天气怎么样？
# 模型可能返回：
{
  "name": "get_weather",
  "arguments": {
    "city": "北京"
  }
}
```

程序收到后：
- 执行 get_weather("北京")
- 把结果再喂给模型
- 模型再生成自然语言回复

##### 4️⃣ Function Call 的本质

Function Call ≠ 工具本身

它本质是：LLM → 结构化意图表达协议

### 二、什么是 MCP（Model Context Protocol）
##### 1️⃣ MCP 的一句话定义

MCP 是一个标准化协议，用来让模型“统一、安全、可发现地”使用外部工具和资源。

如果说：

- Function Call 是 “我想调用一个函数”
- 那 MCP 是 “函数、工具、数据、上下文的统一接口规范”

##### 2️⃣ MCP 解决的根本问题

在 MCP 之前，工具接入是这样的：

- 每家模型：不同 function schema、不同 tool 定义方式
- 每个应用：重写一套工具适配、强耦合某个 LLM 平台

👉 严重碎片化

MCP 的目标是：一次定义工具，多模型通用

##### 3️⃣ MCP 能提供什么能力

MCP 不只是“函数调用”，而是三大类能力：

>① Tools（工具）
- API
- 数据库操作
- 命令
- 业务函数

>② Resources（资源）

- 文件
- 文档
- 数据集
- 知识库

>③ Prompts（上下文模板）

- 可复用 prompt
- 结构化上下文注入

##### 4️⃣ MCP 的角色结构（很关键）
```
┌──────────┐
│   LLM    │
└────┬─────┘
     │ MCP 协议
┌────▼─────┐
│ MCP Host │  ← 你的应用
└────┬─────┘
     │
┌────▼─────────┐
│ MCP Servers  │  ← 工具提供方
│ (tools/resources)
└──────────────┘
```

模型 永远不能直接访问工具，只能通过 MCP Host 间接调用

### 三、Function Call 与 MCP 的关系
##### 1️⃣ 核心关系一句话

Function Call 是能力，MCP 是协议与生态

##### 2️⃣ 对比表
| 维度   | Function Call | MCP              |
| ---- | ------------- | ---------------- |
| 层级   | 模型能力          | 系统协议             |
| 关注点  | “怎么调用函数”      | “怎么组织所有工具和上下文”   |
| 是否标准 | ❌ 各家不同        | ✅ 统一协议           |
| 范围   | 单个函数          | 工具 + 资源 + Prompt |
| 复用性  | 低             | 高                |
| 解耦   | 弱             | 强                |


##### 3️⃣ 类比理解

- Function Call ≈ syscall
- MCP ≈ POSIX / HTTP

##### 4️⃣ 实际调用关系

在 MCP 内部：模型仍然是通过 Function Call 形式

但：
- schema 是 MCP 统一规范
- 工具是可发现的
- 资源是结构化可引用的

👉 MCP 是 Function Call 的“上层标准化封装”

### 四、为什么需要 MCP？（使用的必要性）
##### 1️⃣ 不用 MCP 会发生什么

当系统变复杂：
- 工具 > 10 个
- 模型 > 2 种
- 团队 > 1 个

你会遇到：
- 工具定义重复
- prompt 到处拷贝
- LLM 绑定特定厂商
- 安全边界混乱
- 难以测试和调试

##### 2️⃣ MCP 的核心价值（工程视角）
✅ 解耦

- 工具 ≠ 模型
- 工具 ≠ prompt
- 工具 ≠ 应用

✅ 标准化

同一工具可被：**GPT、Claude、本地模型、Agent 系统** 复用

✅ 可治理

- 权限控制
- 工具白名单
- 访问审计

✅ 可扩展

- 新工具 = 新 MCP Server
- 不改模型逻辑

##### 3️⃣ 什么时候“必须”用 MCP？

建议使用 MCP 的场景：多模型并存、Agent 系统、插件生态、企业级应用、长期维护项目

不一定需要 MCP 的场景：Demo、单模型 + 少量工具、一次性脚本
