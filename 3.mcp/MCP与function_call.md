# 🧩 一、为什么“以前单单调用 Tool 容易不准”？

典型老方式是：

* 模型只通过 prompt 或简单 JSON schema「猜」：

  * 有哪些工具？
  * 应该什么时候用？
  * 参数到底怎么填？

容易出问题：

| 问题      | 表现                         |
| ------- | -------------------------- |
| 工具发现差   | 模型不知道 / 忽略工具               |
| 参数理解错   | key 拼写错、类型不一致              |
| 语义歧义    | “domain”和“company”傻傻分不清    |
| 边界条件差   | 空字段 / None / Optional 处理崩掉 |
| 错误返回不规范 | 模型无法判断到底失败还是正常             |
| 没有元信息   | 工具能力描述不够，模型乱猜用途            |

👉 **这些问题本质上不是大模型“智力不够”
而是“缺乏一个稳定规范的交互协议”。**

---

# 🚀 二、MCP 具体是怎么改善这些问题的？

## ✅ 1️⃣ 工具是「被声明出来」的，而不是“隐形存在”

在 MCP 里：

> MCP Server 必须正式告诉模型：
> 我有哪些工具、每个工具是什么、怎么用

包括：

* 名字
* 描述（docstring）
* 入参 JSON Schema
* 类型约束
* 必填字段
* 默认值
* 返回结构描述

**→ 模型不用猜工具能力**

就像 API 有 swagger/openapi 文档一样。

---

## ✅ 2️⃣ 参数是「强结构化」的

例如：

```python
class Clue(BaseModel):
    customer_id: str
    email: str | None = None
    domain: str | None = None
```

转成 JSON Schema 后：

* 必填：`customer_id`
* 允许为空：`email/domain`
* 类型：string
* 不允许传 int/bool/随机字段

🌟 **fastmcp / MCP client 会自动校验：**

* 如果模型发错
* 不是你来撞 N 次才知道
* 而是直接报一个结构化错误

→ **减少大量低级错误**

---

## ✅ 3️⃣ 工具描述对模型是清晰友好的

比如你的 docstring：

```python
"""
根据线索获取或更新客户画像。
"""
```

模型会：

* 把这个内容读进上下文
* 理解这个工具什么时候能解决问题

相比：

> prompt 里一句话模糊提醒
> “有个函数可以查公司信息”

**清晰度完全不是一个级别**

---

## ✅ 4️⃣ 调用结果是结构化 & 可预期的

例如：

```python
class Profile(BaseModel):
    customer_id: str
    company_name: str | None = None
    risk_level: str | None = None
```

返回一定是 JSON。

* 不会混入说明文字
* 不会出现 “{"data": {...}} 或 {"result": {...}}" 乱定义
* 不会忽然改字段名

→ **模型更容易持续使用结果做推理**

---

## ✅ 5️⃣ error handling 更标准

例如：

* 参数错
* 超时
* 外部 API 掉了

MCP 会返回**规范化错误结构**

而不是：

```
{"error": "接口异常"}🤯
```

模型可以更稳定地：

* 重试
* 换方法
* 询问用户
* 退出

---

## ✅ 6️⃣ 能力发现更系统

模型可以：

* 一次性看到所有工具
* 理解它们的 schema
* 决定调用策略

而不是：

> “啊？你说还有个工具？我不知道啊”
