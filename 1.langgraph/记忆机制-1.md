简短说：LangGraph 的“记忆”其实是**两套东西**：

1. **短期记忆（short-term / 线程记忆）**
2. **长期记忆（long-term / 各种 store）**

它们是靠 **graph state + checkpoint + store** 这三件套拼起来的。

---

## 1. 短期记忆：基于 State + Checkpointer 的“线程记忆”

在 LangGraph 里，每次对话/会话都对应一个 **thread**，thread 里的状态就是你的“短期记忆”。

* 你定义一个 `State`（一般是 Pydantic/BaseModel 或 TypedDict），里面通常有 `messages`、中间结果之类。
* 图在执行的时候，**状态会在节点之间流动**，每走一步就可以被 **checkpointer** 存一份快照（checkpoint）。
* 只要你下次调用时带上同一个 `thread_id`，它就会从对应的 checkpoint 把状态恢复出来，这样就能“记住”前面的对话。([LangChain Docs][1])

典型写法（Python）：

```python
from typing import Annotated, TypedDict
from langgraph.graph import StateGraph
from langgraph.checkpoint.memory import MemorySaver  # 或 InMemorySaver

class State(TypedDict):
    messages: list

builder = StateGraph(State)

def chat_node(state: State):
    # 这里读取并更新短期记忆（messages）
    ...

builder.add_node("chat", chat_node)
builder.set_entry_point("chat")

checkpointer = MemorySaver()  # 或 InMemorySaver / SqliteSaver / PostgresSaver ...
graph = builder.compile(checkpointer=checkpointer)

# 第一次对话
graph.invoke(
    {"messages": [{"role": "user", "content": "你好"}]},
    config={"configurable": {"thread_id": "user-123"}}
)

# 第二次对话（带同一个 thread_id），会自动带上之前的 messages
graph.invoke(
    {"messages": [{"role": "user", "content": "继续刚才的话题"}]},
    config={"configurable": {"thread_id": "user-123"}}
)
```

这里的关键机制是：

* **State = 当前短期记忆**（例如最新若干条 messages）。
* **Checkpointer = 状态持久化组件**，官方提供好几种：内存版、SQLite、Postgres、Redis 等。([LangChain Docs][2])
* **thread_id = 会话 ID**，用来把同一个用户的多轮对话归到同一条“时间线”上。

> 如果用的是 `MemorySaver` / `InMemorySaver`，数据只在进程内存里，不会真正落库，重启就没了；换成 `SqliteSaver`、`PostgresSaver`、Redis 等，就可以做真正的持久化。([LangChain Docs][2])

## 2. 长期记忆：基于 Store 的“知识/偏好记忆”

短期记忆只是这条线程的对话上下文；**长期记忆**是指：

* 用户资料（偏好、历史事实）
* 长期知识（文档、FAQ、知识库）
* 跨会话共享的信息（不只限于一个 thread）

LangGraph 这部分是通过 **store（文档存储 / 向量库）**实现的：([LangChain Docs][3])

典型思路：

1. 用 `InMemoryStore` / 自己的数据库 / 向量库作为 memory store
2. 节点里根据当前对话内容去 **检索相关记忆**（semantic search）
3. 把检索到的结果拼到 prompt 里
4. 模型回复后，根据回复再 **写回/更新记忆**

示意代码：

```python
from langgraph.store.memory import InMemoryStore

store = InMemoryStore()  # 真实项目可换成向量库、Redis、PG 等

NAMESPACE = "user_profile"

def load_long_term_memory(user_id: str):
    docs = store.search(namespace=NAMESPACE, query=f"user_id:{user_id}")
    return docs

def save_long_term_memory(user_id: str, content: str):
    store.put(
        namespace=NAMESPACE,
        key=f"user-{user_id}",
        value={"user_id": user_id, "content": content}
    )
```

然后在某个 graph 节点里：

* 先 `load_long_term_memory(user_id)`，把内容塞进 system/prompt
* 生成回复后，根据需要再 `save_long_term_memory(...)` 更新

## 3. “记忆”到底是怎么组织起来的？

从架构上看，可以理解为：

1. **状态（State）**：

   * 描述当前这次调用的上下文（messages、工具结果等）
   * 通过 reducer（合并函数）从上一步 state + 当前节点输出合成下一个 state

2. **Checkpoints（短期记忆持久化）**：([LangChain Docs][1])

   * 每走到一个“超级步”（super-step）就可以自动保存一份 checkpoint
   * checkpoint 存的是“thread_id + 当前 state”
   * 再次调用时用同一个 thread_id，就能恢复到之前的 state

3. **Stores（长期记忆）**：([LangChain Docs][3])

   * 把结构化/半结构化的记忆以 `namespace + key + value(JSON)` 的形式存储
   * 可以做搜索（关键词 / 语义向量）
   * 用在“记住用户偏好”“知识库问答”等场景

## 4. 实战上一般这么用

**一个典型“带记忆的聊天机器人”用 LangGraph 的套路：**([LangChain Docs][1])

1. 定义 `State`，包含 `messages` 等。
2. 用 `StateGraph` 搭建节点：

   * `router`：判断是否需要查知识库 / 更新长期记忆
   * `retriever`：从向量库/DB 里检索长期记忆
   * `assistant`：调用 LLM，prompt 里拼上短期 + 长期记忆
   * `writer`：根据当前对话内容决定是否写入长期记忆
3. 编译时配置 `checkpointer`，实现短期记忆持久化。
4. 每次前端调用都传入统一的 `thread_id`（如用户 ID 或会话 ID）。
5. 如果是多实例/多机部署，再用 Redis / Postgres / 自己的 DB 做 checkpointer + memory store。

## 5. 如果你在想“我自己的项目该怎么设计记忆？”

简单给你三条实践建议（够用）：

1. **先用短期记忆搞定多轮对话**

   * 直接上 `MemorySaver` + `thread_id`，先让机器人能“接话”。
   * 上生产再换 `SqliteSaver`、PostgresSaver、RedisSaver 等。

2. **再根据业务加长期记忆**

   * 用户偏好、用户档案 → 用普通数据库/JSON store
   * 文档/知识库 → 用向量库（Chroma、PGVector、Redis、Zep 等），在节点里做检索 + 写回。

3. **记忆不是越多越好，要“裁剪”**

   * 短期记忆：只保留最近 N 条消息 / 做摘要（LangGraph 有裁剪/总结示例）。([LangChain Docs][1])
   * 长期记忆：用标签、命名空间、分片来组织，避免一股脑全部塞给模型。
